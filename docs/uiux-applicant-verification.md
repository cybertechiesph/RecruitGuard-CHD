## 5. Rework list (for a follow-up implementation pass)

Ordered by severity; both are small and neither blocks shipping. **Both were implemented and verified live in a follow-up pass — Batch D, commit `d0a44ce`, on `main`.**

1. **UX-09 — stop the form-level error-clearing from wiping still-valid file errors.** In `recruitment/templates/recruitment/applicant_intake_form.html`, the `form.addEventListener("input", clearError)` / `("change", clearError)` handlers call `clearFieldErrors()`, which removes every `[data-client-error]` node — including a file-slot error whose invalid file is still selected. Smallest fix: in `clearFieldErrors()` (or a wrapper used by the form-level listeners only), skip error nodes whose associated input still has the `data-file-validation-error` attribute set, and keep the slot's `--error` class for those. Acceptance: select a `.txt` in a Step-2 slot, then type in "Summary of your qualifications" — the file error text and red slot state must remain until the file is replaced or removed.

   **→ Resolved (Batch D).** `clearFieldErrors(preserveActiveFileErrors)` skips the error node, `is-invalid`, and red slot for any input still holding `data-file-validation-error`; only the form-level `clearErrorOnEdit` passes that flag, so per-field `clearClientErrorForField` still clears fully. Verified live (SQLite + seeded data) at 375px: select `letter.txt` → error + red slot; type in the qualification summary → error text, red slot, and `is-invalid` all persist (previously wiped); replace with a valid PDF → all clear.
2. **UX-03 — ship the Tier-2 upload progress for the success path (optional but planned).** Add an `XMLHttpRequest` POST of `new FormData(form)` in `verifyReadabilityThenSubmit()` with `xhr.upload.onprogress` driving a percent readout in the existing `#rg-intake-progress` status line; on `load` follow `xhr.responseURL` when it differs from the current URL; on network `error`/`timeout` re-enable the button as "Try again" with the planned copy ("The upload did not go through — check your connection and try again. Your typed answers are still here."). Keep the current Tier-1 native-submit behavior as the fallback when the fetch/XHR path errors synchronously and for no-JS. Acceptance: under DevTools Slow-3G a moving percent shows during upload; killing the network mid-upload shows the retry state with fields intact.

   **→ Resolved (Batch D), with one flagged interaction.** `uploadForm` now POSTs `new FormData(form)` via `XMLHttpRequest`: `xhr.upload.onprogress` drives the `#rg-intake-progress` percent, `load` follows `xhr.responseURL`, and `error`/`timeout`/`abort` show the "Try again" copy; native `form.submit()` stays the fallback for no-JS and synchronous XHR failure. Verified live: readout `"Uploading… 100%"` captured from a ~2.7 MB upload (an intermediate *moving* percent needs real network throttling — not reproducible headlessly — but the onprogress→percent mechanism is confirmed); a connection-refused submit showed the retry state with every typed field + selected file intact; a full XHR intake → OTP → receipt (9 files) round-trip completed. **⚠️ Interaction:** the XHR follows the 302 itself, so it (not the browser) fetches `/otp/` and consumes the one-time "draft is ready" flash — **UX-07 shows that alert 0× on the XHR path** (still 1× on the native / no-JS fallback). The dedup fix is untouched (no duplicates anywhere) and the OTP page still shows "we sent a code to the applicant email", but this changes UX-07's "exactly one alert" behaviour on the XHR path. Inherent to `responseURL`-following (the plan ruled out the `document.write` alternative that keeps the flash); a small server endpoint returning the redirect URL for XHR would avoid the double-GET if the flash should be preserved.
